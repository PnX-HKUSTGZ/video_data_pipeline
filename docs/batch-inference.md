# 单卡批量推理

`batch_size` 指一次送入模型的图像数量，同时支持检测和 YOLO pose。输入视频先按既有规则解码、采样，再将同一视频的待推理帧组成批次；保存视频时，组批的对象是全部源帧。

```yaml
device: 4
batch_size: 8
```

默认值为 `1`，要求正整数，不接受布尔值、小数、字符串或自动模式。现有配置未填写时保持逐帧推理。CLI 覆盖示例：

```bash
uv run --locked video-dataset run --config configs/rm26_exchange_pose.yaml \
  --batch-size 8 --output datasets/generated/rm26_exchange_pose/batch8_new
```

多视频继续使用同一个模型顺序处理；每个视频结束时处理剩余帧，不跨视频组批。默认视频在 2 FPS 下产生 1320 张图：batch 8 调用模型 165 次，batch 16 调用 83 次，其中末批有 8 张。没有填充、重复帧或丢帧。

## 处理规则

- `Detector.predict_batch` 接收图像列表，返回与输入一一对应的逐帧检测列表；保留 `predict` 单帧接口。
- 只接受尺寸一致的图像批次，并保持矩形预处理、640 推理尺寸及原有 FP32 设置。结果数量不符立即报错。
- 每张图独立进行类别内 NMS，框和关键点共用筛选索引，不会在不同帧之间抑制目标。
- 结果按源顺序执行阈值筛选、预览、JSONL 写入及导出，时间戳和帧号不变。时间划分、伪标签规则及 schema 6 保持原样。
- `save_video: true` 时仍然逐帧处理、逐帧保存，batch 只影响模型每次接收的数量。`sample_fps` 仍被忽略，正数 `smoke_frames` 仍禁止使用。
- 内存只缓存有限批次的原图及处理临时量，不缓存整段视频。batch 增大会增加 GPU 和主机内存占用。
- 显存不足会报告运行失败，不自动减小 batch 或改变精度。失败时不写完成标记，沿用暂存图片和编码半成品清理流程。

## 验证方法

性能对比使用原始 `recvlnoyv3arV6_红方工程第一视角.flv` 全片、2 FPS、640、FP32 和原有模型/阈值，分别测试 batch 1、4、8、16。每次使用独立进程，包含模型加载、数据导出及真实 Ultralytics 数据校验；GPU 可见性在导入 CUDA 库前配置。

本轮 GPU4 有其他任务，性能对比显式使用空闲 GPU0（RTX 4090），仓库默认设备仍为 4。记录每次完整流程耗时、`predict_batch` 调用累计耗时、调用次数，以及 PyTorch 峰值已分配/保留显存；显存指标不包含 CUDA 上下文等额外开销。

不同 batch 可能改变 GPU 数值计算的舍入结果，因此逐项对比采样帧、筛选/划分、目标类别与数量、框坐标及关键点有效标记，不以标签文件必须逐字节相同作为批量推理的正确性条件。

## 性能结果

下表为本机单次测量，单位为秒；完整流程包含加载、解码、导出及数据校验。首次检测 batch 1 与 CPU 功能测试重叠，因此额外在测试结束后复测，表中使用复测值；首次 43.11 秒及复测 36.45 秒均保留原始记录。共享主机的 CPU、磁盘负载会影响整流程耗时，数值不表示固定加速比。

| 模型 | batch | 完整流程 | predict_batch 累计 | 峰值已分配显存 MiB |
| --- | ---: | ---: | ---: | ---: |
| detect | 1 | 36.45 | 6.93 | 96.2 |
| detect | 4 | 33.77 | 4.18 | 170.4 |
| detect | 8 | 37.41 | 3.59 | 270.7 |
| detect | 16 | 53.78 | 23.36 | 474.2 |
| pose | 1 | 37.20 | 7.05 | 97.5 |
| pose | 4 | 35.01 | 4.13 | 171.5 |
| pose | 8 | 34.67 | 4.34 | 271.7 |
| pose | 16 | 52.79 | 22.27 | 475.2 |

当前条件下可先尝试 batch 4，再按实际视频和保存选项比较 batch 8。检测 batch 4 的完整耗时比复测 batch 1 低约 7.3%；pose batch 8 低约 6.8%。GPU 推理调用虽明显减少，但解码、图片写入和验证仍占主要耗时。batch 16 在两个模型上均更慢，不推荐直接以最大 batch 作为默认值。库和现有配置继续默认 batch 1。

检测复测证据位于 `detect_b1_confirm/`；用于此表的记录集中在 `benchmark_summary.json`。峰值保留显存也保存在各 `metrics.json`，本次范围约为 120–656 MiB；CUDA 上下文和非 PyTorch 开销另计。

## 数值对比

检测模型在 batch 1/4 下均收录 351 张训练图、80 张验证图和 676 个框；batch 8/16 为 350/80 和 675 个框。关键点模型所有批次大小均为 361/83 张图片、767 个框和 4627 个有效关键点，逐帧筛选/划分及关键点有效标记一致，但坐标值不是逐位相同。

检测差异已定位到 218.0 秒的第 5450 帧：其 pillar 框分数在 batch 1/4/8/16 下分别为 `0.501879`、`0.500154`、`0.499669`、`0.499730`，batch 8/16 因而低于原有 0.5 阈值。诊断时单独将模型输出阈值降至 0.1 来读取该预测，没有修改正式数据生成阈值。同一帧在单张和批量预处理后的 GPU 张量逐元素完全一致，形状为 `[3,384,640]`，排除了预处理或帧对应差异。

当前环境沿用 PyTorch 的 `cudnn.allow_tf32=True` 和 `cuda.matmul.allow_tf32=False`。仅在独立诊断进程中关闭 cuDNN TF32 后，四种 batch 的该框分数都约为 `0.503689`；诊断结束后恢复设置，生产代码没有修改这些选项。FP32 张量并不保证不同 batch 的 GPU 内核输出逐位相同，阈值附近的检测可能跨过边界。

此外 batch 4 在第 9325 帧少一个原分数为 `0.500167` 的框，该帧本来就在划分间隔内，不影响最终训练/验证计数。逐帧差异及最大坐标偏差保存在验收目录的 `comparisons.json`；阈值诊断详见 `numerical_check/results.json`。

## 测试与产物

全仓 293 项测试、核心包严格 mypy、Ruff 检查和格式检查通过。新增检查覆盖配置/CLI、单批/多批/末批、帧序与标签对应、跨视频收尾、空检测、逐图 NMS 与框点对应、保存全部视频帧，以及批次异常和错误结果数量的清理。

另以 batch 8 对两段视频的 `[200,210)` 区间保存推理视频。两段均为 1920×1080、25 FPS、10 秒和 250 帧，源帧号 5000–5249 连续，末批 2 帧完整保留。输出数据为 169/43 张训练/验证图、384 个框、2337 个有效关键点，与此前逐帧运行的计数一致，实际 Ultralytics 加载通过。

本轮验收跨越 2026-10-06/07，结果统一保存在 `datasets/generated/batch_validation_20261006/`：

- `detect_batch8/`、`pose_batch8/`：两种模型的全片 batch 8 数据集，包含 `COMPLETE.json` 和校验结果。
- `pose_video_batch8/`：两视频逐帧保存的 batch 8 数据集及视频。
- `detect_b*/`、`pose_b*/`：各次性能运行的配置、报告、验证结果、日志、显存指标和 GPU 快照；这些目录仅是验证证据，不是可训练的数据集。
- `metrics.json`、`comparisons.json`：原始性能数据及逐帧数值差异。
- `numerical_check/results.json`：阈值附近预测的独立数值诊断。

batch 1/4/16 的重复图像产物属于临时性能测试输出，比较结束后清理，仅保留上述证据；原视频及此前的数据集保持原样。日志使用已有轮转配置，编码临时文件、暂存图片、临时脚本及 Ultralytics 标签缓存均已清理。
